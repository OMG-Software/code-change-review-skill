# Axis: Generated and Reproducible Output

Load when the change edits generated code, changes a generator or the source it reads (`.proto`, OpenAPI, GraphQL schemas, templates), touches snapshot or golden files, or writes output that must be the same on every run (checked-in or compared files, build artifacts, cache keys, content hashes). Use with `review-angles.md`.

- Generated code edited by hand (a file headed "Code generated … DO NOT EDIT", protobuf or OpenAPI output, an ORM's migration snapshot): the next regeneration silently drops the edit. The fix goes in the source or the generator.
- Source changed but the generated output not regenerated, or regenerated with a different generator version from the one the project pins: the checked-in output no longer matches what the build or other services produce.
- Derived files that must move together: a lockfile and its manifest, a schema and its generated client, a translation catalogue and its source strings, a snapshot of a migration's model state. Check each pair the change touches on one side.
- Determinism, where the output must be reproducible: a generated file that is checked in or compared with a fresh build, a build artifact, a cache key or content hash, a snapshot. Such output must not depend on an order that is unspecified or can change between runs (Go map iteration, Python `set` of strings under hash randomization, Java `HashMap`/`HashSet`, directory listings), the current time or an unseeded random source. An order the language guarantees is fine when its input is itself reproducible: insertion order in JavaScript `Map`/`Set`, Python `dict` or Java `LinkedHashMap`, or any sorted collection. A generator that ranges over a Go map can produce a different file on each run, so "is the generated file up to date?" checks fail at random and every regeneration shows churn. Randomness the output exists to have (keys, salts, nonces, tokens, randomized signatures) is exempt; removing it is the defect.
